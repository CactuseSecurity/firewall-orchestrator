# Systemd units

## Unit locations

All systemd units owned by the installer are written to the local unit directory
`/etc/systemd/system`. Up to release 11.0 they were installed into the vendor directory
`/lib/systemd/system`, which belongs to the package manager and is not the correct place for
units maintained by an administrator or an installer.

The following units are managed:

| Unit | Written by |
| --- | --- |
| `fworch-hasura-api.service` | `roles/api` (generated by `podman generate systemd`) |
| `fworch-middleware.service` | `roles/middleware` |
| `fworch-ui.service` | `roles/ui` |
| `fworch-importer-api.service` | `roles/importer` |

The relevant variables are defined in `inventory/group_vars/all.yml`:

| Variable | Meaning |
| --- | --- |
| `fworch_systemd_unit_dir` | directory new units are written to (`/etc/systemd/system`) |
| `fworch_systemd_vendor_unit_dir` | legacy directory, only used for detection and cleanup (`/lib/systemd/system`) |
| `fworch_systemd_unit_search_dirs` | both of the above, local directory first - used when looking for an already installed unit |
| `fworch_systemd_unit_names` | all unit names owned by fworch, including legacy Hasura service names |
| `fworch_systemd_restart_sec` | restart delay applied to all fworch services |

## Upgrading an existing installation

Units are not simply left in both places. On an upgrade the roles write the unit into
`/etc/systemd/system` and `roles/finalize/tasks/relocate-systemd-units.yml` then removes the
superseded copy from `/lib/systemd/system`.

That task also runs `systemctl reenable` for every unit whose vendor copy it removed. This is
required because systemd matches enablement symlinks by unit name: a symlink in
`multi-user.target.wants` that still points into the vendor directory keeps reporting the service
as `enabled` while no longer resolving to a unit file, so the service would silently not start on
the next reboot.

## Startup ordering and restart behaviour

Services order themselves after `network-online.target` rather than `network.target`, and pull the
target in via `Wants=`. Note that `network-online.target` is only reached when a wait-online
implementation is enabled - `NetworkManager-wait-online.service` on RedHat, `systemd-networkd-wait-online`
or `networking.service` on Debian. If none is enabled, the ordering is simply a no-op; if one is
enabled but an interface never comes up, boot is delayed by that unit's timeout.

Since the actual dependencies of the fworch services are local (PostgreSQL, slapd, the API), the
ordering that matters most is expressed explicitly:

- the middleware orders after the API service and `slapd.service`
- the UI and the importer order after the API and the middleware service
- the Hasura API service orders after `postgresql.service` when the database runs on the same host

The Hasura unit is generated by podman, so its ordering cannot be templated. It is applied through
a drop-in at `/etc/systemd/system/fworch-hasura-api.service.d/fworch-startup.conf`, which survives
regeneration of the unit.

All services set `Restart=` together with `RestartSec` (from `fworch_systemd_restart_sec`) and
`StartLimitIntervalSec=0`. Without disabling the start rate limit, a service that fails fast while
a dependency is still starting burns through the systemd default of five restarts within ten
seconds and ends up in a permanent `failed` state - which is what caused fworch services not to
come up after a reboot on RedHat.

## Debugging

```console
systemctl status 'fworch-*'
systemctl cat fworch-hasura-api.service      # shows the unit plus all drop-ins
systemctl list-unit-files 'fworch-*'         # shows the enablement state
journalctl -u fworch-hasura-api -b -1        # log of the previous boot
```
